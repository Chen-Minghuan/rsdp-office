## 目标与验收

触发：用户在左侧项目需求面板点击“总结”。
结果：白色原文面与灰色 AI 总结面是同一张卡片的正反两面，点击“总结”整卡 3D 翻转到灰色总结面，再次点击翻回白色原文面；总结控件为铜棕滑动开关，“总结”文字位于开关内。编辑按钮位于总结左侧。

范围：

- 面板位于项目与楼层上方；空间核对页的原有需求块不套用新面板。
- 每次进入和刷新默认原文；只有用户点击才显示总结。
- AI 总结仅用于展示，下游排版、推荐和报价仍使用客户原文。
- 真实模型事实抽取，保留数字、单位、预算、否定和限制，不固定凑四条。
- 原文与总结分开保存，缓存绑定原文修订、模型和提示词版本。
- 本轮不包含预热、SSE、双模型复核或跨 JVM 请求合并。

- [x] 默认原文，点击成功后才翻转，再次点击返回原文。
- [x] AI 失败保留原文并提示；旧请求不能污染新项目或新版本。
- [x] 相同原文版本读取持久化缓存，不重复调用模型。
- [x] 原文修改后旧版本总结不能保存为当前结果。
- [ ] 更多真实客户文本的准确率和延迟业务验收。

## 实现与契约

接口：

```text
POST /api/v1/office/projects/{projectId}/requirements/summary
请求：{"requirementsRevision":3}
响应 data：{"keyPoints":["……"],"sourceRevision":3,"cacheHit":false}
```

后端从数据库读取当前项目原文，核验项目成员权限、非空及 4000 字上限。模型使用 `qwen3-vl-plus`，可通过 `RSDP_REQUIREMENTS_SUMMARY_MODEL` 覆盖；密钥和兼容地址继续由 `DASHSCOPE_API_KEY`、`DASHSCOPE_BASE_URL` 提供。请求关闭思考和流式输出，温度为 0，响应只接受 `keyPoints` JSON 列表，校验空白、重复、数量和单点长度。

`office_design_project` 新增：

- `requirements_summary JSONB`
- `requirements_summary_revision`
- `requirements_summary_model`
- `requirements_summary_prompt_version`
- `requirements_summary_generated_at`

需求编辑通过专用 Mapper 原子执行 `requirements_revision = requirements_revision + 1`，避免并发编辑产生相同修订号。总结通过专用 Mapper 使用 `CAST(#{summaryJson} AS jsonb)` 并按项目 ID 与原文修订号条件更新，不覆盖原文。相同版本的进程内请求合并仅对当前单 JVM 生效。
