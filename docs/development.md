# 开发规范与执行流程

更新日期：2026-10-13。项目目标见 [产品需求](product-requirements.md)，长期修改规则见 [AGENTS](../AGENTS.md)。

## 1. 每项工作开始前

1. 读取项目规则、进度表、相关需求和代码；区分原型、当前实现及本轮目标。
2. 查看工作区差异，保留既有改动，限定本次任务的影响范围。
3. 用任务模板写清具体目标、依赖、输入输出、验收与验证方法。
4. 跨识别、画布、排版、推荐服务的任务先明确契约，再实现接口和交互。
5. 将状态更新为进行中，按可独立验证的小步骤推进。

小型文案和配置修正可以简化记录，涉及空间几何、业务状态、商品生命周期和跨服务契约的变更需要任务文件。

## 2. 代码与模块约定

- 沿用 Nuxt/Vue、Pinia、Java/Spring、.NET CAD 的现有目录和代码风格。
- 页面组织交互；坐标转换、几何编辑、排版检查放入有明确输入输出的模块，不散落在模板与事件处理里。
- Java 控制器负责协议和参数校验，服务负责业务规则与外部调用；CAD 服务负责 CAD 几何解析。
- 外部识别、推荐、生成服务使用独立客户端与适配层，错误、超时及版本信息统一传回业务层。
- 关键接口使用有类型的 DTO/schema；来源不确定的数据先校验，再转换。新增核心几何逻辑不依赖随意 `any` 强转。
- 真实商品资料、价格、尺寸和可用性由后端核验，前端显示不得成为唯一业务约束。
- 现有数据库结构变化采用明确迁移方案；不通过重复初始化脚本假定已有数据已迁移。
- 保留原始识别和历史确认快照；可编辑草稿、来源几何、派生数据和视图状态职责分开。
- 稳定 ID、坐标与单位、版本、数据来源遵守 [架构契约](architecture.md)。

## 3. 产品交互规范

- 按“识别 → 空间编辑（复核提示） → 排版确认 → 推荐 → 方案确认 → 效果图”推进，允许返回修改并明确影响。
- 空间和家具编辑使用实际单位；px、服务地址、请求细节只在必要诊断信息里展示。
- 页面区分正在加载、没有数据、部分结果、失败、待校准、待人工复核、已确认和过期结果。
- 参数无效或布局放不下时明确反馈，不将估算值和静默回退表示为成功。
- 演示数据显示其来源，不能自动进入正式确认或代替真实服务验收。
- 保存状态以实际保存结果为准；失败有可恢复草稿和清楚反馈。
- 正式推荐/生成的阶段条件由后端检查；用户直达 URL 或刷新不能绕过。

## 4. 必须验证的核心不变量

| 范围 | 必须成立的行为 |
| --- | --- |
| 商品 | 上下架可恢复；下架不进入新推荐；旧方案引用不被静默删除 |
| 识别 | 来源可追溯；未知单位不当已校准；失败和演示可识别 |
| 画布 | 导入保留真实轮廓；各层对齐；平移/缩放不改实际尺寸 |
| 尺寸编辑 | 数值、轮廓、面积和保存数据一致；撤销/恢复后仍一致 |
| 排版 | 与当前空间版本一致；实际尺寸和旋转占地参与边界/碰撞检查 |
| 推荐 | 基于已确认布局；选定商品及变体真实可用且满足匹配要求 |
| 效果图 | 绑定已确认快照；过期响应不成为当前结果 |

容差应注明单位、来源和理由，并在对应任务固定。没有明确业务依据时，不把计算容差包装成行业标准。

## 5. 当前已有验证入口

以下命令按影响范围选择，不要求文档变更运行业务系统全量测试。

| 检查 | 命令/入口 | 前置条件及范围 |
| --- | --- | --- |
| 前端构建 | 在 `frontend/` 执行 `pnpm build` | 已安装依赖；不代替独立类型检查或业务验收 |
| UI 工作流 | 在 `frontend/` 执行 `pnpm e2e:workflows` | 前端服务运行、浏览器可用；拦截 API，验证已有 UI 用例 |
| UI 冒烟 | 在 `frontend/` 执行 `MOCK_API=1 pnpm e2e:smoke` | 前端运行；接口隔离模式，不代表真实服务结果 |
| Java 测试 | `mvn -f backend/pom.xml test` | Java/Maven 和测试依赖可用 |
| CAD 测试 | `dotnet test backend/cad-parser/tests/RsdpCadParser.Tests/RsdpCadParser.Tests.csproj` | 当前目标 `net7.0`；核对金样本是否实际存在 |
| 差异检查 | `git diff --check`，检查相关文件差异 | 不混入无关、临时和生成文件 |
| 文档检查 | 本地链接、命令、目标/现状及状态表一致性检查 | Markdown-only 变更适用 |

独立 lint/typecheck 和统一 CI 当前尚未配置，不能把计划中的命令写成已执行检查。
CAD 金样本缺失时部分用例会提前返回，即使报告通过也不能据此认为对应样本已验收。

## 6. 按任务补充有意义的测试

- 商品上下架：真实服务中重复切换、刷新恢复、推荐过滤、已选商品变化处理。
- 识别适配：矩形、异形、未命名、多图目标、单位不明、错误响应；验证数据转换和来源映射。
- 画布几何：正逆变换、底图对齐、负坐标/大坐标、拖动与数值编辑一致性、撤销/重做和保存恢复。
- 排版：旋转后边界、异形凹角、孔洞/柱、家具碰撞、放不下、空间修改后布局失效。
- 流程：不能跨过未确认阶段；返回修改使正确的下游状态失效，未受影响空间保持。
- 生成：快照一致性、过期响应、失败重试和重复提交。

单元测试适合几何和状态规则；UI 测试适合交互；真实集成验证适合服务、文件及数据库链路。
三类证据分别记录。真实样本标明文件哈希/版本和预期，不仅保存截图或 HTTP 200。

## 7. 任务完成与文档同步

业务任务从“已编码待验证”进入“已验收”需要：

1. 任务验收标准得到实际验证，相关核心不变量成立。
2. 记录代码版本、命令、结果、真实/模拟环境和未覆盖事项。
3. 受影响 README、架构契约、任务记录和进度表已更新。
4. 剩余需求明确拆到后续任务，不能用“基本完成”隐藏验收缺口。

受限于环境未执行的验证标为未执行；失败保留原因和下一步。文档任务以文档完整性、一致性和链接检查验收。
提交内容写清问题和结果，例如 `feat(canvas): preserve imported room polygons`；
PR/交付说明包含行为变化、验证结果和必要限制。沿用用户已授权的提交、推送或发布范围，不引入默认自动推送规则。

## 8. 进度与过程维护

`status.md` 维护当前状态；单项任务保存实施过程和证据；重大契约决定更新 `architecture.md` 并在任务中说明原因。
阶段切换、发现需求差距、完成验证或出现阻塞时更新记录。
不从代码行数、页面数量或估计百分比推断功能完成，也不把“代码存在”当成“已验收”。
任务完成后记录下一步，让新一轮开发能从文件继续，无需重读整段聊天。
